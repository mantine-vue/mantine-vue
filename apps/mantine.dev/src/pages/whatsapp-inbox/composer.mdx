## Capability-driven

Every composer action is driven by the `capabilities` you supply per conversation. Nothing about a
particular provider's feature set is hard-coded, so a backend that cannot do something simply does
not advertise it and the control disappears.

<Demo data={WhatsAppComposerDemos.capabilities} />

```ts
import type { WhatsAppConversationCapabilities } from '@mantine-vue/whatsapp-inbox'

const capabilities: WhatsAppConversationCapabilities = {
  canSendFreeForm: true,
  canSendTemplates: true,
  canSendMedia: true,
  canSendInteractive: true,
  canUseEmoji: true,
  canReplyToMessage: true,
  canRetryFailed: true,
  interactiveTypes: ['button', 'cta_url'],
  allowedMediaTypes: ['image', 'document'],
  maxTextLength: 4096,
  mediaConstraints: {
    image: { maxFileSize: 5 * 1024 * 1024, accept: ['image/jpeg', 'image/png'] },
    document: { maxFileSize: 100 * 1024 * 1024, maxFiles: 1 },
  },
  messagingWindow: { state: 'open' },
  disabledReason: undefined,
}
```

Only `canSendFreeForm` and `canRetryFailed` default to `true`; everything else is off until you
turn it on. `resolveCapabilities()` is exported if you want the same defaults in your own code.

Individual `with*` props override the capabilities for one screen, without changing what the
backend allows:

```vue
<WhatsAppComposer :capabilities="capabilities" :with-attachments="false" />
```

## Sending

`send` carries a discriminated union on `kind`, so your handler can switch over it exhaustively.
Each payload carries a `clientId` generated by the composer – use it to reconcile the optimistic
message with the one your backend echoes back.

<Demo data={WhatsAppComposerDemos.sending} />

```ts
type WhatsAppOutgoingMessage =
  | { kind: 'text'; conversationId: string; clientId: string; replyTo?: string; text: string }
  | { kind: 'media'; /* … */ attachments: WhatsAppAttachment[]; caption?: string }
  | { kind: 'template'; /* … */ name: string; language: string; values: WhatsAppTemplateValues }
  | { kind: 'interactive'; /* … */ interactive: WhatsAppInteractiveContent }
```

The draft is cleared and the reply target reset as soon as `send` is emitted; whether the message
actually goes out is up to you. Report progress back with `sending` and `error`.

## Keyboard

Enter sends and Shift+Enter inserts a newline. A send is never triggered mid-composition, so IME
input is not cut off. Turn the shortcut off with `:send-on-enter="false"`.

## Validation

Validation is a UI concern, so the composer owns it. A draft is refused before anything is emitted
when it is empty, longer than `maxTextLength`, or when an upload is still in flight. The reason is
shown in the composer and emitted through `validationError`.

## Emoji

The package ships a WhatsApp-style picker, and `canUseEmoji` is all it takes to get it: search,
category tabs that follow the scroll position, sticky category labels, a recently-used row,
arrow-key navigation and a hovered-emoji preview.

<Demo data={WhatsAppComposerDemos.emoji} />

The popover stays open after a pick, so a run of emoji goes in without reopening it, and the
character lands at the caret rather than at the end of the draft.

### Choosing which emoji are offered

`emoji-picker-props` configures the built-in picker. Filtering works from either direction: keep a
few categories with an allow-list, or start from everything and remove with a block-list.
`filter` gets the final say on whatever survives.

<Demo data={WhatsAppComposerDemos.emojiFiltering} />

<DataTable
  head={['Prop', 'Effect']}
  data={[
    [<Code>groups</Code>, 'Allow-list of categories, rendered in the order given'],
    [<Code>excludeGroups</Code>, 'Categories to drop'],
    [<Code>emojis</Code>, 'Allow-list of characters'],
    [<Code>excludeEmojis</Code>, 'Characters to drop'],
    [
      <Code>filter</Code>,
      'Predicate over the surviving entries, for anything the lists cannot express',
    ],
    [<Code>emojiData</Code>, 'Replaces the built-in dataset entirely'],
  ]}
/>

A category that filters down to nothing loses its tab, so the strip never offers an empty section.

The other picker props cover layout and behaviour: `columns`, `width`, `height`, `withSearch`,
`withTabs`, `withPreview`, `withRecent` and `recentLimit`.

### Recently used

The picker keeps its own recently-used list for the lifetime of the component. Bind
`recentEmojis` to persist it:

```vue
<WhatsAppComposer
  :emoji-picker-props="{
    recentEmojis: recent,
    'onUpdate:recentEmojis': (value) => {
      recent = value
      localStorage.setItem('wa-recent-emoji', JSON.stringify(value))
    },
  }"
/>
```

### Replacing the picker

Supply an `emojiPicker` slot and it takes precedence over the built-in one. Pair it with
`:with-emoji-picker="false"` to make the intent explicit.

<Demo data={WhatsAppComposerDemos.emojiCustom} />

With the built-in picker off and no slot supplied, the emoji control stays hidden rather than
opening an empty popover.

The dataset is a curated set rather than the full Unicode catalogue, and it carries no skin-tone
variants — a complete catalogue would cost every consumer a large bundle for something most
inboxes do not need. When you need one, `emojiData` swaps the dataset while keeping the picker, and
the slot replaces the picker outright.

### Using the picker on its own

`WhatsAppEmojiPicker` is exported, so it works outside the composer — a reaction bar, a status
editor, anywhere:

<Demo data={WhatsAppComposerDemos.emojiStandalone} />

```vue
<script setup lang="ts">
import { WhatsAppEmojiPicker } from '@mantine-vue/whatsapp-inbox'
import type { WhatsAppEmoji } from '@mantine-vue/whatsapp-inbox'

function handleSelect(emoji: WhatsAppEmoji) {
  react(emoji.emoji)
}
</script>

<template>
  <WhatsAppEmojiPicker :columns="9" height="300px" @select="handleSelect" />
</template>
```

The filtering helpers behind it are exported too, for building your own UI over the same data:

```ts
import { filterEmojis, searchEmojis, WHATSAPP_EMOJIS } from '@mantine-vue/whatsapp-inbox'
```

## Replies

With `canReplyToMessage` the composer renders a quote above the input, bound with
`v-model:reply-to`. The referenced id ends up in the outgoing payload as `replyTo`.

## Drafts

The composer's own `v-model` is a single string. Per-conversation drafts – keeping an unsent
message when the user switches away and restoring it on return – live one level up, on
[`WhatsAppConversation`](/whatsapp-inbox/conversation) and
[`WhatsAppInbox`](/whatsapp-inbox/inbox), which are the components that know the conversation id.

## Disabled for other reasons

`capabilities.disabledReason` covers everything that is not the messaging window – a conversation
the current agent may not write to, a suspended number, a read-only view. The composer disables
the input and explains why.

```ts
const capabilities = {
  canSendFreeForm: false,
  disabledReason: 'This conversation is assigned to another agent',
}
```

For the 24-hour window specifically, see [messaging window](/whatsapp-inbox/messaging-window).

## Accessibility

- The input is labelled, and every control has an accessible name.
- The closed-window notice is a `role="status"`; send and validation failures are `role="alert"`.
- The character count is a polite live region.
- The emoji popover traps focus while it is open.
